# 2026-10-20 —— 产品闭环改造：AgentTeams、四个亮点玩法与「星轨」视觉系统

> **归档快照，不回改。** 后续变更请新增一份带日期的快照。

---

## 1. 背景

需求是「按游戏开发流程跑一次完整闭环」：调研 → 产品 → 设计 → 开发 → 测试 → 验收，
并同时完成文档分层、UI 美化、bug 修复与亮点建设。

当时的现状（基线提交 `c4efa1b`）：

| 维度 | 现状 |
|---|---|
| 题库 | 12 域只有 6 域有题，合计 260 题 |
| 玩法 | 每日挑战 / 同步抢答 / 错题本 —— 缺"明天为什么回来"的钩子 |
| 视觉 | 深灰底 + 单一橙强调色，emoji 当图标，无动效层 |
| 文档 | AGENTS.md 塞满业务逻辑；docs/ 只有 PRD 与部署手册 |
| 质量 | typecheck / 171 测试 / 题库校验全绿 |

---

## 2. 决策一：建立 AgentTeams（产品生产团队）

**决定**：用 6 个角色化子 Agent 跑流水线，角色卡落在 [`agents/TEAM.md`](../../agents/TEAM.md)。

| 角色 | 阶段 | 交付物 |
|---|---|---|
| AT-01 调研员 | 调研 | `docs/research/` 竞品拆解 + 差异化机制候选 |
| AT-02 产品经理 | 产品 | `docs/PRD.md`（活文档） |
| AT-03 设计师 | 设计 | `docs/design/ui-system.md` + 落地 |
| AT-04 工程师 | 开发 | 代码 + 单测 |
| AT-05 测试 | 测试 | 用例 + 缺陷分级 |
| AT-06 验收官 | 验收 | 逐条对账报告 |

**理由**：闭环的难点不是"把活干完"，而是**阶段之间有出口条件**。
每个角色有明确交付物与 gate，就不会出现"看起来做完了其实没验证"。

**并行规则（硬约束）**：同一时刻一个文件只能有一个 owner。
子 Agent 的 brief 必须写明「你唯一拥有的文件」与「你绝对不得修改的文件」。

> 实战教训：并发上限是 4。7 个内容任务同时派发时 3 个被拒。
> 分批派发即可，不要把"被拒"当失败。

## 3. 决策二：四个亮点玩法（全部零服务端成本）

约束是硬的：**不破坏每日挑战的无状态架构，不引入账号体系，不增加服务端状态**。

| 玩法 | 一句话 | 为什么成立 |
|---|---|---|
| **影子对手** | 和过去的自己同场竞速 | 排行榜需要服务端 + 账号 + 反作弊；影子只需要 localStorage |
| **通识段位** | 六段成长线（见习→睿哲） | 由本地生涯累计算出，与每日反馈互补 |
| **盲盒轮转** | 1 个本命 + 2 个每日盲盒 | 纯函数、按日期种子，强制跨域 |
| **同题 PK 码** | 同一个码 = 同一份题 | `buildDailySet` 本就支持显式 seed，两人各自本地跑即可 |

**同题 PK 码**是这一轮最关键的设计发现：项目里最独特的资产是「全网同题」，
但此前只被用作排行榜的底座 —— 而排行榜恰恰做不出来。
把 seed 的来源从"房间 seed"换成"日期 + 码"的哈希，
**「全网同题」就从一句技术特性变成了社交货币**。

**明确的边界（不粉饰）**：PK 没有实时同步、没有自动判胜、换设备不共享进度。
这些都写进了 PRD，而不是藏在实现里。

## 4. 决策三：「星轨 / Orbit」视觉系统

**诊断**：旧 UI 的问题不是"不够好看"，是**低能量** —— 全站一个强调色，其余全是灰阶，
12 个领域的主题色完全没被用上。

**决定**：建立完整 token 体系（`tailwind.config.ts` + `app/globals.css`），
并引入"星云"母题：**选中的领域把主题色注入背景**（`--nebula-1/2/3`），
于是「选了什么领域」直接改变整个页面的氛围。

同时完成三件基建：
1. **emoji → Lucide SVG**（`lucide-react` 本来就是依赖，只是没用）；
2. **`prefers-reduced-motion` 全局归零**（此前完全缺失）；
3. **可点击目标 ≥44px**、答对/答错**颜色+图标+文案三重线索**。

## 5. 决策四：文档分层

| 文档 | 读者 | 内容 |
|---|---|---|
| `README.md` | 人类新手 | 快速启动、项目概览、玩法一览 |
| `AGENTS.md` | AI | 四条红线、技术栈、极简命令、索引 |
| `docs/*.md` | 人 | 长篇设计、业务规则、API、架构、内容、测试 |

**红线**：AGENTS.md **绝不放业务逻辑**。计分公式进 `GAME-RULES.md`，
API 细节进 `API.md`，题库规范进 `CONTENT.md`。
AGENTS.md 只回答"改代码前必须知道什么"。

## 6. 决策五：验收方式 —— 浏览器实点，而不是只看单测

单测全绿的情况下，**每日挑战的单选与判断题其实完全无法作答**。

根因：`toggleOption` 用 `setTimeout(() => submit(), 0)` 等 `setPicked` 生效，
但 `submit` 是 `useCallback`，闭包捕获的是**点击前那一帧**的 `picked`（空串），
于是命中「答案为空」的分支**静默 return** —— 点了选项毫无反应。
服务端 e2e 全绿，因为**它从不经过客户端 hook**。

**修复**：答案跟着调用走 —— `submit(option)`，不依赖时序。

**由此确立的验收方式**：UI 改造**必须在浏览器里实际点一遍**，
不能只看 `typecheck` 与单测。检查清单见 `docs/TESTING.md` §5。

> **已知缺口**：Playwright 尚未接入 CI，客户端 hook 仍无自动化回归。
> 这是这一轮最值得补的下一步。

## 7. 这一轮没有做的事

| 没做 | 原因 |
|---|---|
| 服务端排行榜 | 需要账号与反作弊，与"无状态云轨"冲突；影子对手已覆盖留存需求 |
| 实时 PK 同步 | 房间态在进程内存，多实例会撕裂；同题离线 PK 零成本达成同等社交效果 |
| 题库扩到每域 60 题 | 本轮先补齐 12 域 × 40 题的底线；重复率是下一轮的题 |
| 待审池运营界面 | 独立工作量，本轮只保留 AI 接口与 10 步校验链 |
| Playwright 回归 | 已知缺口，已在 `docs/TESTING.md` 记录 |

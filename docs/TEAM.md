# AgentTeams —— 《通识局》产品生产团队

> **这是活文档。** 随项目演进持续更新。
> 团队章程（怎么协作、怎么验收）见本文；项目本身的架构红线见 [`../AGENTS.md`](../AGENTS.md)。

---

## 0. 为什么有这支团队

《通识局》不是「写个 App」，它是一个**每日都要有人回来**的游戏。产品的成败不取决于代码量，
而取决于三件事同时成立：

1. **题目值得读** —— 解析是知识密度来源，不是凑数文案；
2. **画面值得看** —— 界面是有品味的设计，不是默认样式的堆叠；
3. **明天有理由回来** —— 每天一个新的钩子。

所以团队按**游戏开发流水线**组织，每个阶段有明确的**交付物**与**出口条件**（gate），
不靠"感觉差不多了"推进。

---

## 1. 流水线（六阶段闭环）

```
 ① 调研 Research ──▶ ② 产品 Product ──▶ ③ 设计 Design ──▶ ④ 开发 Dev ──▶ ⑤ 测试 QA ──▶ ⑥ 验收 Acceptance
       │                   │                  │                │              │                │
  竞品拆解            玩法定义            视觉系统          编码落地        用例+回归        逐条对账
  开源借鉴            需求排期            组件规范          代码评审        缺陷分级        PASS/FAIL
  缺口清单            验收标准            交互规格                           覆盖率          遗留清单
       │                   │                  │                │              │                │
       └───────────────────┴──────────────────┴────────────────┴──────────────┴────────────────┘
                                          ↺ 验收不通过 → 回到对应阶段
```

**出口条件（gate）**：

| 阶段 | 出口条件（不满足就不许进下一阶段） |
|---|---|
| ① 调研 | 每个外部结论都带可访问 URL；差异化机制候选已按「成本 × 新颖度」排序 |
| ② 产品 | 每条需求都有**可验证**的验收标准（不是"要好用"） |
| ③ 设计 | 产出可直接落地的 token（hex / 字号 / 圆角 / 动效时长）与组件规格 |
| ④ 开发 | CI `verify` 全绿；不破坏任何架构红线 |
| ⑤ 测试 | 新增逻辑有单测；全量回归无退化；发现的缺陷已分级并修复 |
| ⑥ 验收 | 逐条需求对账，**证据**（文件路径 / 命令输出 / 渲染结果）齐备 |

## 2. 角色卡

六个角色对应六个阶段。**同一时刻只有一个角色是"当前责任人"**（parallel writer 除外），
其余角色产出评审意见。每个角色都必须遵守 [`../AGENTS.md`](../AGENTS.md) 的架构红线。

### AT-01 调研员 · Researcher

| | |
|---|---|
| **使命** | 在动手前，先知道别人已经做对了什么、还没做什么 |
| **输入** | 项目现状、PRD、现有实现 |
| **交付物** | `docs/research/<日期>-<主题>.md`：竞品 UI 拆解、开源项目借鉴点、差异化机制候选（按成本×新颖度排序）、视觉与文案规范建议 |
| **出口条件** | 每条外部结论带来源 URL；无法验证的明确标注"未能验证" |
| **红线** | 只读项目文件；外部结论必须实检，不许凭记忆编造 |
| **常见坑** | 把"我觉得"当"调研"；只罗列竞品功能不给可落地的结论 |

### AT-02 产品经理 · Product

| | |
|---|---|
| **使命** | 把"新鲜感"变成**可验收的玩法**，而不是一句形容词 |
| **输入** | 调研报告、现有 PRD、架构红线 |
| **交付物** | `docs/PRD.md`（活文档）：领域体系、四条产品线（§5）、**新增玩法的规则与验收标准**、路线图 |
| **出口条件** | 每条需求都写明"玩家看到什么 / 系统做什么 / 怎么算通过" |
| **红线** | 不新增破坏无状态架构的需求；不改领域/种子/日期口径 |
| **常见坑** | 需求写成愿望（"更好玩"）；漏掉空态与边界（首日、断签、改领域） |

### AT-03 设计师 · Designer

| | |
|---|---|
| **使命** | 让"知识问答"看起来像一款**有品味的游戏**，而不是一个表单 |
| **输入** | PRD、调研报告、现有 `tailwind.config.ts` 与 `app/globals.css` |
| **交付物** | `docs/design/ui-system.md` + 落地改动：设计 token、组件规格、动效规格、文案规范 |
| **出口条件** | 每个视觉决策都给出可直接写进代码的 token 值（hex / px / ms） |
| **红线** | 依赖克制见 [`../AGENTS.md`](../AGENTS.md) §2.4；深色主题一致性；信息层级不能压过可读性 |
| **常见坑** | 动效过度导致答题节奏拖沓；对比度不足；只换颜色不换层级 |

### AT-04 工程师 · Engineer

| | |
|---|---|
| **使命** | 把设计变成**跑得通、测得住**的代码 |
| **输入** | PRD 的验收标准、设计 token、架构红线 |
| **交付物** | 代码改动 + 对应单测 + 变更说明 |
| **出口条件** | CI `verify` 全绿（静态检查 + 单测 + 内容校验 + 构建）；红线未被破坏 |
| **红线** | 见 `AGENTS.md` §2（每日挑战无状态 / 服务端权威 / 凭证纪律 / 依赖克制） |
| **常见坑** | 共享逻辑只测一侧（见 `AGENTS.md` §6.2）；顺手重构无关文件 |

### AT-05 测试 · QA

| | |
|---|---|
| **使命** | 在交给用户之前，先把崩溃和退化找出来 |
| **输入** | 全部改动、验收标准 |
| **交付物** | `__tests__/` 新增用例、缺陷清单（按严重度分级 + 复现步骤 + 证据） |
| **出口条件** | 全量回归通过；每个新逻辑都有对应断言；**客户端主流程由 `e2e/`（Playwright）在 CI 里守住** —— 改动 `hooks/**`、`components/quiz/**`、`app/{daily,pk,duel,wrong}/**` 时先补/改对应 e2e 用例，跑 `npm run test:e2e`；脚本断不了的（视觉层级、文案语气、动效节奏）才按 [`docs/TESTING.md`](TESTING.md) §5.3 人工看 |
| **红线** | 不修改被测实现（发现问题交给 AT-04）；测试纪律见 [`docs/TESTING.md`](TESTING.md) §2–4 |
| **常见坑** | 只测 happy path；把实现值当断言。判据见 [`docs/TESTING.md`](TESTING.md) §2–4 |

### AT-06 验收官 · Acceptance（Verifier）

| | |
|---|---|
| **使命** | **不相信任何人的口头结论**，逐条对账 |
| **输入** | 原始目标、全部交付物、仓库当前状态 |
| **交付物** | 验收报告：逐条需求 → 证据 → 结论（PASS / FAIL / PARTIAL）+ 遗留清单 |
| **出口条件** | 每条需求都有**独立取证**；不能取证就标 PARTIAL 并写明缺什么 |
| **红线** | 只读；不改交付物；不修 bug（只报） |
| **常见坑** | 把"看起来对"当"验证过"；用窄检查支撑宽结论 |

## 3. 协作协议

### 3.1 编排者（Orchestrator）

由**编排者**担任（哪个 agent 取决于当前运行环境，不绑定具名工具）。职责：
- 决定**阶段顺序**与**并行批次**，避免两个 writer 同时改一个文件；
- 为每个任务写**自包含的 brief**（子 agent 看不到父会话上下文）；
- 复核子 agent 的产出（**子 agent 的输出是证据，不是结论**）；
- 汇总到最终交付说明。

### 3.2 并行写入的硬规则

> **同一时刻，一个文件只能有一个 owner。**

- 派发任务时必须写明"你唯一拥有的文件"和"你绝对不得修改的文件"；
- 需要改共享文件（如 `content/domains/index.ts`）的任务，由编排者自己执行；
- 子 agent 报告的**其他文件的报错**，一律不许顺手修 —— 那是别人的 owner。
- **并发上限由编排器决定**（本仓当时实测为 4，属环境值，不是本项目的规则）。一次派发超过上限会被拒 ——
  分批派发即可，不要把"被拒"当失败。

### 3.3 命名与归档

- 调研快照：`docs/research/<日期>-<主题>.md`，文件名带日期；
- 设计系统：`docs/design/ui-system.md`（活文档）；
- 产品需求：`docs/PRD.md`（活文档，持续更新）；
- 团队章程：本文（活文档）。

文档分层、决策归档与“调研快照不回改”的规则见 [`../AGENTS.md`](../AGENTS.md) §6。
